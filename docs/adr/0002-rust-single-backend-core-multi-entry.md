# ADR 0002 — Rust 单后端内核与多入口适配层

- **日期**：2026-03-16
- **状态**：提议中（未落地）
- **决策者**：@alexc

---

> 来源：原 plans 文档《2026-03-16 Rust 多入口后端化设计》（plans 目录已整体删除，本文是该设计的决策提取）。

## 背景

CardMind 的长期方向已经收敛为：Flutter 前端 + Rust 后端、LoroDoc 唯一真实信源 + SQLite 查询侧读模型。
但当时 Rust 能力的对外形态仍偏向「面向 FRB 的内嵌后端门面」，尚未收敛为可被多入口复用的统一内核；
其后果是：后续任何新入口都只能从 FRB 门面上外挂，容易把某个协议的形状误当成后端接口。
本设计的目标不是做远程部署平台，而是在 Flutter App 项目形态下建立「单 Rust 后端内核 + 多入口适配层」的稳定架构，
并把「多入口契约一致」作为首要验收目标。

## 决策

1. **Rust 是唯一后端内核**；FRB、CLI、HTTP、MCP 都只是入口适配层，不复制业务规则、不直接改写存储事实。
2. **FRB 是 Flutter App 的默认主入口，默认启用**；CLI、HTTP、MCP **默认不启用**。
3. 可选入口的启用状态由 **Rust 侧配置文件持久化**管理，而不是由 Flutter 临时页面状态决定。
4. **HTTP 第一阶段仅监听回环地址**（127.0.0.1 / localhost），但监听地址在设计上属于入口配置的一部分，
   预留未来可配置化的演进空间；第一阶段不引入外网访问、远程部署、安全鉴权或公开服务暴露。
5. **MCP 的定位是 AI/Agent 工具入口**，而不是对现有 HTTP API 的简单别名。
6. **CLI 的定位是调试/运维入口**，不是面向普通终端用户独立分发的外部产品。
7. **应用服务层是唯一正式后端接口**：稳定的后端接口应是用例语义，而不是 FRB 函数签名、HTTP 路由形状、
   CLI 命令格式或 MCP tool 名称；各入口必须经应用服务层访问后端，不得直接耦合底层 store、network 或历史门面函数。
8. **四入口必须共享**：用例语义、DTO 核心字段、错误码、成功/失败/降级状态语义、读写链路约束。
   **不必完全共享**：参数承载方式、协议包装形式、输出格式细节、交互风格。
9. **错误契约以稳定 error.code 为核心**，message 用于展示/调试，details 只作诊断、不能驱动产品级业务分支；
   入口层只做协议翻译，不得重定义成功/失败边界。
10. **状态语义至少区分三类**：业务写成功、投影未收敛、同步未收敛；四入口含义一致，
    入口不得把投影失败或同步失败伪装成业务写失败；入口运行时故障（监听失败、服务启动失败等）必须与业务故障区分。
11. **启用后的入口在 App 运行期间必须真实可达**：配置标记为 enabled 而没有实际运行实例不合格；
    配置变更必须驱动当前运行时真实启停，并由统一的运行时入口管理器持有句柄、健康状态与关闭逻辑。

## 拒绝的方案

### 方案 B：以 HTTP API 为中心，CLI/MCP 尽量复用 HTTP

- 优点：外部接口形状更统一，调试抓包方便。
- **拒绝理由**：会把本机内核能力过早绑死在 HTTP 资源表达上；CLI 与 MCP 容易退化为 HTTP 套壳；
  不利于保持 MCP 的工具语义（MCP 应是工具语义，而不是路由的复刻）。

### 方案 C：在现有 FRB API 基础上继续外挂入口

- 优点：短期改动最小、起步最快。
- **拒绝理由**：最容易把「面向 FRB 的门面」继续误演化为唯一后端接口；长期放大历史命名与分层包袱；
  难以从根上证明 Rust 已成为面向多入口的后端内核。

### 被否决的边界扩张

- 第一阶段不做远程部署/云端能力扩张；HTTP 不提前引入外网访问与鉴权（见决策 4）。

## 后果

- **正向**：多入口契约一致有结构性保障；新增入口不需复制业务规则；FRB 主路径行为保持稳定。
- **成本/负向**：需要一次明确的模块重整（domain / application / infrastructure / runtime 分层），
  并补齐统一应用服务层、配置模型与运行时入口管理层（含句柄、健康状态、错误状态与关闭逻辑）。
- **流程约束（当时）**：落地前必须先补齐正式规格对 Rust 后端边界、入口能力与运行时行为的约束，
  再把规格更新与索引一致性检查列入实现计划的首批任务，而不是附带事项。

### 现状核对（2026-10）

- **该设计的代码部分未落地**：仓库中不存在 HTTP / MCP / CLI 入口实现，也不存在 http_enabled、mcp_enabled、
  cli_enabled 之类的入口配置；`rust-backend/src/api.rs` 仍是唯一的对外导出面，Rust 后端目前只经 FRB 服务 Flutter。
- 因此本文记录的是**当时锁定的架构方向与契约原则**，不是当前实现事实。若后续要恢复多入口计划，
  应把「应用服务层是唯一正式接口」「契约一致性」两条作为验收基线。
