# ADR 0007 — 双向链接与全文搜索的数据契约

- **日期**：2026-08-12
- **状态**：已采纳
- **决策者**：@alexc

---

> 来源：原 plans 文档《分布式个人知识库 — 二期实现计划》
> （plans 目录已整体删除，本文是该计划中锁定的数据/协议约束与范围决定）。
> LoroDoc 容器 v1→v2 的结构与迁移另见 ADR 0001。

## 背景

二期把 CardMind 从笔记同步应用升级为分布式个人知识库，MVP 优先级为
双向链接（P0）、全文搜索（P1）、标签元数据化（P2）。
架构保留 Flutter + Rust（Loro CRDT + iroh + SQLite），改动集中在 LoroDoc 容器结构、
SQLite 新表与索引、FRB API 与编辑器。

其中需要长期固定的是一批**数据与协议约束**：笔记 id 形态、链接在正文中的语法、
链接索引的事实来源、搜索索引的分词与降级策略。

## 决策

1. **笔记 id 用 UUID v7**（时间有序）；id 不作为容器内字段，只存在于 LoroDoc 的键与 SQLite 中。
2. **链接语法固定为 `[[target-id|alias]]`**，别名缺省时取 target_id；链接只从正文（content 容器）解析。
3. **links 表是读投影，不是事实源**：每次投影同步末尾先删除该笔记的出链，再按解析结果整表重建
   （主键 `source_id + target_id`，附 alias）。
4. **悬空链接保留数据行**：目标笔记不存在时，链接行仍在，靠与笔记表的 LEFT JOIN 判定
   `exists = false`，由 UI 呈现为灰色/已删除，而不是删除链接数据。
5. **全文搜索用 SQLite FTS5 + trigram 分词**：虚表覆盖标题、正文、标签，content 指向 notes 表、
   由触发器跟随 notes 的增删改维护。
6. **中文短查询降级**：trigram 要求查询至少 3 个字符，因此 **< 3 字符时回退到原有的 LIKE 搜索**；
   ≥ 3 字符走 MATCH + bm25 排序，并用 snippet 取匹配上下文；特殊字符（双引号等）转义后作为短语查询。
7. **保留既有 LIKE 搜索方法不动**，新搜索方法独立命名，避免替换既有行为。
8. **标签读写改为走元数据（meta Map）**，正文不再承载标签注释；正文中残留的标签注释只在迁移/兼容路径处理。
9. **FRB API 一次加全**（链接/反链/搜索/补全/标签/元数据），避免 UI 阶段再分散追加接口。
10. **二期明确不做的四件事**：知识图谱可视化、笔记删除 API、P2P 实时链接查询、多人协作。

## 拒绝的方案

### 在二期引入笔记删除 API

- **源文给出的理由**：链接行在投影同步时全量重建，笔记消失后链接随之自然消失，不需要为删除单独设计编排。
- **（推断）**：引入删除 API 会扩大二期的数据一致性面——源文未写这条理由。

### 把链接与搜索做成 P2P 实时查询

- **源文**：只把该项列入「明确不做（二期范围外）」，未给理由。
- **（推断）理由**：本项目链接与搜索都是本地读投影（正文解析 → links 表、FTS5），
  跨设备实时查询会引入网络可用性与一致性的额外风险。

### 把知识图谱可视化、多人协作纳入二期

- **源文给出的范围决定**：二者列在「明确不做（二期范围外）」标题之下。
- **（推断）**：图谱属 P3 能力、多人协作与「单人使用、多设备 P2P 同步」冲突——
  这两条依据来自当前 `docs/product.md`，不是当时的源文。

### 在 UI 阶段再逐步补后端 API

- **源文给出的理由**：FRB API 一次加全；任务 B 依赖任务 A 生成的 FRB 代码，必须顺序执行。
- **（推断）**：分批加接口会让 UI 与后端契约反复对齐——源文未写这条理由。

### 用 FTS5 直接替换既有 LIKE 搜索

- **源文给出的理由**：trigram 要求查询至少 3 个字符、< 3 字符需要回退既有 LIKE 逻辑；
  源文明确「保留现有 `search()` 方法（LIKE）不动，新方法独立命名」。

## 后果

- **正向**：链接与搜索都不进入 CRDT 热路径，只读投影；悬空链接可见、可恢复；
  搜索有 bm25 排序与上下文片段。
- **约束/负向**：
  - 中文短查询语义受分词限制（< 3 字符退回 LIKE，排序与相关性不可比）；
  - links 表是全量重建的派生数据，任何直接写入 links 的行为都会被下一次投影覆盖，不能当作事实源；
  - 链接解析依赖正文语法，正文里写坏的 `[[...]]` 不会产生链接行。

### 现状核对（2026-10）

- **已落地**：`rust-backend/src/store.rs` 建 notes / links / notes_fts 三张相关表与 FTS 同步触发器，
  投影同步末尾重建出链，出链/反链查询用 LEFT JOIN 判定 `exists`，搜索实现 < 3 字符回退；
  `rust-backend/src/api.rs` 导出 generate_note_id、note_update_metadata、get_outgoing_links、
  get_backlinks、search_notes、auto_complete_links、get_all_tags、search_by_tag。
  链接语法解析见 `rust-backend/src/sync.rs` 的 `parse_links`（`[[target|alias]]`，无别名时别名 = id）。
- **第 10 条中的一项后来被推翻**：笔记删除 API 现已存在——软删除、恢复、回收站列表与过期清理
  （`rust-backend/src/api.rs` 的 note_soft_delete / note_restore / store_trash_list / purge_expired_trash），
  删除状态（`deleted_at`）是来自 Loro 的读投影，store 不独立决定删除。
  其余三项（知识图谱可视化、P2P 实时链接查询、多人协作）仍未做：
  `docs/product.md` 把知识图谱列为 P3、把多人协同编辑列为不做。
- **容器版本已继续演进**：当前信封版本为 3（墓碑 section + 记录流），v1→v2 的迁移路径仍保留。
