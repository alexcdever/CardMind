# ADR 0006 — 跨设备同步的技术选型：Loro + iroh + mDNS

- **日期**：2026-07-08
- **状态**：已采纳
- **决策者**：@alexc

---

> 来源：原 plans 文档《第二阶段调研：局域网同步》
> （plans 目录已整体删除，本文是该调研中锁定的选型与协议决策）。

## 背景

v2 本地体验确定可用后，下一阶段目标是**局域网设备发现 + 自动数据同步**：
两台设备在同一 WiFi 下无需手动配置即可发现对方并同步笔记。
当时的 v2 状态是 Flutter 直接操作 sqflite，要达成该目标必须重构数据层；
当时需要在「同步整个数据库文件」「自研同步协议」「CRDT + P2P 库」三条路线之间做技术选型。

## 决策

1. **采用 Loro（CRDT）+ iroh（P2P）+ mDNS 的组合**：
   - Loro 提供合并零冲突的 CRDT 语义与 import/export 变更集能力；
   - iroh 提供 QUIC 连接与身份基础（`SecretKey` → `NodeId`，TLS 加密），并**不自带 mDNS**；
   - 局域网发现由 Rust 侧 `mdns-sd` 实现，发现到的地址交给 iroh 建立连接。
2. **Rust 端全权负责数据管理与同步，Flutter 只做 UI 渲染**：
   Rust 侧持有 Loro 真源、iroh 网络、mDNS 发现与 SQLite 读模型；Flutter 侧只渲染。
3. **真相源边界（协议/数据约束）**：编辑器只写 LoroDoc（唯一写入入口），
   LoroDoc 投影到 SQLite 供列表与搜索查询；**Loro 永不读 SQLite，SQLite 永不写 Loro**。
   引入 Loro 前已有的 SQLite 数据做一次性导入迁移，迁移完成后 Loro 接管所有写入。
4. **同步粒度按笔记**：每篇笔记一个 LoroDoc/LoroText，只同步发生变化的笔记
   （相比「整个笔记库作为一个 LoroDoc」更轻量），代价是需管理多个文档。
5. **冲突合并静默完成**：两端离线期间修改同一篇笔记时，由 CRDT 保证合并结果确定、无冲突。
6. **设备发现走标准协议而非手工配置**：注册并扫描局域网服务，把发现的地址交给 iroh；
   手动输入 IP 只作为降级方案，不做主路径。
7. **准入控制是必须的**：mDNS 发现 ≠ 可连接。纯 mDNS 在公共 WiFi 下会把设备暴露给任意人，
   因此首次发现陌生设备需要人工确认（当时方案：批准后的 `NodeId` 进入白名单，
   白名单随笔记数据同步以实现信任传递，新设备只需与已信任设备配对一次）。

## 拒绝的方案

### 方案 B：同步 SQLite 数据库文件

- 优点：实现极简，无需 CRDT。
- **拒绝理由**：冲突处理粗暴（后写覆盖）；无法做到部分更新；不适合后续多用户扩展；
  SQLite 文件不宜直接通过网络传输——与产品未来扩展方向矛盾。

### 方案 C：纯自研同步协议（WebSocket / HTTP）

- 优点：可控、可定制。
- **拒绝理由**：全部从头写、工作量大；仍要自行解决冲突合并；浪费既有成熟库的价值。
  （仅当方案 A 验证不可行时才考虑。）

### 局域网发现的其他备选

- **手动输入 IP**：零复杂度但用户体验差 → 只保留为降级路径，不作为主发现机制。
- **预共享密钥 + 广播**：复杂度与可靠性均为中等 → 不如采用标准 mDNS。
- **依赖 iroh 自带发现**：iroh 不内置 mDNS，需要额外调研 → 不作为主路径。

### 无准入的「发现即可连接」

**拒绝理由**：在公共 WiFi 下等于把设备暴露给任意旁观者；准入判断是必要条件。

## 后果

- **成本**：Rust 端需要自写设备发现、连接管理与同步协议编排；Flutter 数据层需要从 sqflite 迁移到 Rust 后端。
  白名单方案本身的代码量不大（身份、密钥与同步能力已由 iroh 与 Loro 提供），
  维护成本落在「名单随数据同步」这一约束上。
- **风险与应对**：mDNS 在部分路由器/防火墙下不可用（降级：手动输入 IP）；
  QUIC 在严格防火墙下可能被阻断（可经 relay 中转）。

### 现状核对（2026-10）

- **技术选型已落地**：`rust-backend/Cargo.toml` 依赖 iroh、loro、mdns-sd；
  设备发现的服务类型为 `_cardmind._tcp.local.`（`rust-backend/src/discovery.rs`），
  每篇笔记一个 LoroDoc（`rust-backend/src/sync.rs` 的 `NoteCrdt`）。
- **拓扑与 relay 有后续演化**：2026-08-15 的同步网络定稿进一步锁定「必须支持跨网段 + 全对等 mesh +
  启用 iroh relay（公共 relay 起步）」，见 `docs/sync-network.md`；当前实现的默认行为是
  `RelayMode::Disabled`（仅局域网），只有数据目录存在 relay 配置且内容为 URL 时才启用自定义 relay
  （`rust-backend/src/sync.rs`）。因此「relay 作为兜底」在代码上是**可配置项而不是默认值**。
- **准入控制保留，实现方式已更换**：调研提出的「白名单存 LoroDoc 并随笔记同步的信任传递」未采用；
  现在实现为 6 位数字配对码（10 分钟有效、最多 5 次失败）+ 签名配对凭证 + 已配对设备表
  （`rust-backend/src/sync.rs`、`rust-backend/src/store.rs` 的 `paired_devices`）。
  「发现 ≠ 可连接」这一条仍然成立。
- **同步粒度与真相源边界未变**：SQLite 仍只是读投影（`rust-backend/src/store.rs` 的 `sync_note` 只读 LoroDoc）。
