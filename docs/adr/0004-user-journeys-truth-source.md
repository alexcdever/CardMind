# ADR 0004 — 用户旅程层真相源与旅程总原则

- **日期**：2026-03-20
- **状态**：已采纳（载体已删除，原则保留）
- **决策者**：@alexc

---

> 来源：原 plans 文档《用户旅程真相源设计》与《User Journeys Truth Source Implementation Plan》
> （plans 目录已整体删除，本文是该设计的决策提取）。

## 背景

产品级真相源回答的是「CardMind 是什么产品」，但它不回答「用户如何一路感知这个产品成立」。
2026-03-19 的产品审计指出：项目缺少把首次使用、开始记录、跨设备延续、异常恢复和长期信任串起来的
用户旅程真相源，导致 roadmap、交互设计与实现验收容易跳过用户价值闭环，直接落入功能或工程任务视角。

因此需要在产品级真相源之下、交互与领域规格之上，增加一层旅程层正式文档。

## 决策

1. **新增旅程层下游产品规格**（当时为正式规格目录下的用户旅程规格），受产品级上位真相源约束。
   其用途是**产品校准**，不是设计稿说明、功能清单或测试用例集合。
2. **只覆盖个人多设备主路径的五个阶段**：首次理解、开始记录、跨设备延续、异常与恢复、长期使用与信任稳定。
3. **数据池协作不作为并列主阶段**：它只作为个人多设备主路径之外的数据流转扩展情境被引用
   （出现在跨设备延续与异常恢复两处的扩展说明中），以保持「个人多设备优先、协作扩展次之」的产品边界。
4. **每个阶段 MUST 使用统一四项记录格式**：
   用户此时想完成什么 / 用户此时最在意什么 / 产品必须提供的体验承诺 / 旅程成立信号与断裂信号。
5. **文档级约束**：如果一条内容不能帮助判断某段用户旅程是否成立，则不应进入该文档。
   页面布局、组件级实现细节、API/FFI/存储约束、尚未确认的未来扩展能力都不写。
6. **旅程总原则**（用于约束后续所有阶段）：
   1. 先记录，再理解复杂机制；
   2. 主路径优先于扩展能力；
   3. 异常恢复属于主路径的一部分，而不是边缘补丁；
   4. 可信任比功能堆叠更重要；
   5. 如果某项设计不能增强个人多设备笔记流转主路径，应降低优先级。
7. 该文档为交互、领域规格与后续规划提供**校准依据**，但不写死具体 roadmap 决策。

## 拒绝的方案

### 把旅程层写成页面说明、组件设计或测试脚本

**拒绝理由**：会失去产品校准作用，把「旅程是否成立」的判断让位给实现细节；
设计文档明确要求用稳定、可判定、非界面化的语言描述。

### 把数据池协作扩展成与个人多设备主路径并列的主线旅程

**拒绝理由**：与产品级真相源「个人多设备优先、协作扩展次之」的边界冲突；
实施计划也明确禁止这种扩张。

### 靠堆砌描述填充阶段内容

**拒绝理由**：若某阶段的表述无法帮助判断「旅程是否成立」，应回退并重写，而不是继续堆砌描述。

### 发现真相源冲突时靠直觉改写产品目标

**拒绝理由**：若旅程规格与产品级真相源存在语义冲突，应停下更新计划或请人确认，
而不是静默调和——这会把冲突伪装成已决策。

## 后果

- **正向**：roadmap、交互设计与实现验收有统一上游依据；优先级判断可参照用户阶段真相
  （哪些阶段必须优先成立、哪些体验承诺可延后）。
- **约束**：旅程层不替代 roadmap，只为其提供更稳的判定依据；它服务于「旅程成立」，而不是功能扩张。
- **负向**：产品文档层次增加一层（产品级 → 旅程层 → 交互/领域规格），需要维护上下位引用一致。
